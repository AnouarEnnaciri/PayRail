How money is recorded
  • Ledger: append-only entries; every posting has two or more entries summing to zero. BIGINT minor units, MAD only, customer balances can never go negative (CHECK constraints). System balances are derived from the ledger, never stored.
  • Concurrency: accounts are locked FOR UPDATE in UUID order, so opposite transfers cannot deadlock.
  • Transfer states: internal transfers end COMPLETED. External ones go PENDING_SETTLEMENT to SETTLED, FAILED or RECONCILIATION_REQUIRED; from reconciliation only SETTLED or FAILED. A domain check and a PostgreSQL trigger reject anything else.

Design rules behind the scenarios
  • Idempotency: unique (actor, key) with a SHA-256 request hash. Same payload returns the first transfer; a different payload is a 409.
  • Transactional outbox: reservation, ledger posting and event commit together. Workers claim with FOR UPDATE SKIP LOCKED under a lease and cannot finish work after losing it. HTTP calls happen between short transactions.
  • Uncertain outcomes: a timeout, 5xx or 404 is never a rejection. Exhausted retries go to RECONCILIATION_REQUIRED with no refund.
  • One terminal effect: a partial unique index allows a single settlement-or-compensation ledger transaction per transfer.
  • Signed callbacks: HMAC-SHA256 over a length-prefixed payload, constant-time compare, secret of at least 32 bytes, fail-closed when unset, event IDs deduplicated.
  • Reconciliation: detect-only. It checks balances against the ledger, ledger balance, the clearing account and external receipts. Repair is a separate OPS action that re-checks fresh external evidence and records the actor.
